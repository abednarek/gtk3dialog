dialog syntax

Gtkdialog uses an XML-like language. Widget definitions may be read from an environment variable, a file or standard input.

The Since column records the GTKDialog release that added a feature; Legacy denotes an older inherited feature. Features first shipped in the GTK3-only 0.9.1 release are marked 0.9.1. Historical links to GTK2 API pages are retained as source references; the GTK3 backend and unavoidable differences are described in the GTK3 porting notes.

Comments

Comments begin with <!-- and end with -->. They may appear before or after the dialog and between widget definitions.

<!-- Main application window. -->
<window>
	<vbox>
		<!-- Primary action. -->
		<button ok></button>
	</vbox>
</window>

Comments cannot be nested. An unterminated comment is a syntax error. Comment markers inside a double-quoted string are treated as ordinary text.

GTK Property Attributes

Standard writable GTK properties can be set as widget tag attributes. Scalar values must be complete numbers within the range accepted by the GTK property; malformed and out-of-range values are ignored with a warning, so the property's default value remains in effect. Boolean properties accept true, yes or 1, and false, no or 0. These tokens must be complete; numeric prefixes such as 1junk are not booleans.

This generic conversion covers string, Boolean, signed and unsigned integer, floating-point, enumeration and flags properties on the GTK widget that the tag creates. Enumeration values accept a registered GTK3 name or nick, for example GTK_WIN_POS_CENTER or center, as well as the numeric constant. Flags accept a numeric mask or registered names and nicks separated by |, for example button-press-mask | key-press-mask. Names and nicks are case-insensitive.

Supported GdkRGBA properties accept GTK colour specifications such as #123456 or red. Other boxed values and object, pointer and parameter properties cannot be expressed by the generic conversion and are reported as unsupported. Read-only properties and visible are not set here. Constructor arguments, child-packing properties and settings on internal helper widgets are exposed only when the individual widget page names a dedicated Gtkdialog attribute or directive. Consequently the XML language does not claim to expose every item in the GTK3 C API.

Visibility and Sensitivity

The visible="false" widget attribute controls initial visibility. The <sensitive>false</sensitive> directive instead makes a widget insensitive to user input while leaving it visible. The historical <visible>disabled</visible> spelling remains accepted as a deprecated alias for <sensitive>; despite its name it does not hide the widget. At runtime, the show and hide functions control visibility, while enable and disable control sensitivity.

Common widget contract

Every normal XML widget backed by a GtkWidget has the following Gtkdialog facilities. This shared contract also applies to newly added widgets; their individual reference pages describe only the additional operations that are meaningful for their value or native GTK+ class. Declarative helpers such as sizegroup are not GtkWidgets and are explicitly excluded.

  • A <variable> directive names the widget. The export="false" attribute prevents that value from being exported to the shell. Gtkdialog assigns an internal name when the directive is omitted.
  • The <sensitive> directive controls initial sensitivity. The visible tag attribute controls initial visibility.
  • The optional context-menu tag attribute names an exported environment variable containing a <popupmenu> program. Widgets which receive button events open that menu on right click; wrap windowless content in an eventbox when it needs a clickable area. A focused widget opens the menu from the keyboard Menu key or Shift+F10. The menu is created on first use and remains owned by the originating widget.
  • An <action signal="type"> may run a shell command or a Gtkdialog function. The function and condition attributes may be combined with it. An action without signal requires the widget to define a default signal.
  • The common signals are button-press-event, button-release-event, configure-event, enter-notify-event, leave-notify-event, focus-in-event, focus-out-event, hide, show, realize, key-press-event, key-release-event, map-event and unmap-event. Tool buttons forward pointer, keyboard and focus events from their internal GTK+ button to the logical XML widget.
  • The common state functions are enable, disable, show, hide and grabfocus with a widget variable as their parameter. activate is available only when the native widget is activatable; for check and toggle controls it changes their Boolean state, and for radio controls it selects the requested member.
  • The general action functions are break, command, exit, closewindow, launch and presentwindow. The last three window functions require a window variable where applicable.
  • sensitive_is_true/sensitive_is_false, visible_is_true/visible_is_false and variable_is_true/variable_is_false accept any live widget variable. active_is_true/active_is_false require a widget with a Boolean active state. Command and file conditions do not depend on the originating widget.

<default>, <input>, <input file>, <output file>, refresh, save, clear and removeselected are not inherited. They are available only when the individual widget reference describes their value semantics. Likewise, file-monitor and auto-refresh require a widget with implemented file input. block-function-signals affects only functions that can change widget state and emit a signal.

The image-view functions zoomin, zoomout, zoomreset, fit, fitwidth and fitheight require an imageview variable and are documented on that widget's reference page.

reparentwidget:CHILD:DESTINATION[:TAB_LABEL] moves an existing direct child of a box or notebook into another box or notebook in the same window. The child retains its variable, state and actions. A notebook destination uses the optional tab label, or the child's variable name when none is supplied. Invalid targets leave the child in place. See the notebook reference and examples/notebook/notebook_reparent.

settablabel:PAGE:LABEL changes the tab text of a live direct notebook page identified by its child variable. The page content, selection and actions are preserved; LABEL may contain colons or be empty. The action has no effect while the page is outside a notebook.

reorderpage:PAGE:POSITION moves a live direct notebook page to a zero-based tab position. The selected page remains selected and keeps its widgets, values and actions. An invalid position leaves the order unchanged. See examples/notebook/notebook_reorder.

appendtab:TEMPLATE:NOTEBOOK:INSTANCE:LABEL builds a new notebook page from the single-root XML fragment in the environment variable TEMPLATE. Every @INSTANCE@ placeholder is replaced with the requested identifier before parsing; at least one placeholder is required. Identifiers must begin with an ASCII letter or underscore and otherwise contain only ASCII letters, digits or underscores. The label may contain colons. The template variable may instead contain file:/path/to/fragment.xml; the file is read when the action runs. Appending does not select the page unless the notebook was empty.

removetab:INSTANCE destroys only a page created by appendtab, releasing its widget variables, timers and file monitors. Its instance name may then be reused. If a page removes itself inside one of its actions, later actions from that source do not run. Neither action changes pages declared in the original XML. A template must contain exactly one widget root without a surrounding <window>; zero or multiple roots are rejected without adding a page. See examples/notebook/notebook_template.

selecttab:INSTANCE selects a live page created by appendtab. It leaves the current selection unchanged if the instance is unknown or has been removed; it does not address pages declared in the original notebook XML. Use grabfocus:VARIABLE afterward if a child should receive keyboard focus.

appendtabauto:TEMPLATE:NOTEBOOK:LABEL builds a page from the same inline or file-backed XML template as appendtab, assigns a fresh instance identifier, and selects the new page. The identifier replaces @INSTANCE@ in the fragment; a close action inside the fragment can therefore use removetab:@INSTANCE@. In LABEL, @INDEX@ is replaced with the generated sequence number. The identifier spelling is not a stable script interface and is not reused within the process.

A notebook with tab-close-buttons="true" shows a close button on initial and template-created pages. For a template page, tab-close-action runs before closing; its @INSTANCE@ placeholder is replaced with the page identifier. Initial pages close without this action because they have no instance.

hangupterminal:VARIABLE sends SIGHUP to the live direct child recorded by a VTE terminal. It can be used as a notebook's tab-close-action before removing a terminal page. It does not stop descendant processes or guarantee that a child ignoring SIGHUP exits; the action reports unavailability when GTKDialog was built without VTE.

replacebox:TEMPLATE:BOX:INSTANCE replaces the children of a named <hbox> or <vbox> with one XML widget tree. The template source and @INSTANCE@ substitution follow appendtab. The new tree is built before existing children are destroyed, so a missing file or a template with zero or multiple roots leaves the old contents intact. Replacing a child drops its variables, timers and file monitors; an instance can be reused in the same box. Actions following replacebox in a source widget that was destroyed do not run. The inserted root obeys the box's space-expand and space-fill packing settings. See examples/vbox/vbox_template.

Widget Variables

A declared <variable> name is not length-limited by Gtkdialog. Names that are printed or exported must be valid shell identifiers: the first character is a letter or underscore, followed by letters, digits or underscores.

Duplicate names are supported for compatibility with launched windows. Every live widget keeps its own internal mapping, while actions that address a name operate on the most recently declared active widget. Closing that widget makes the previous active declaration addressable again. Output contains one value per name, from that same active widget. Unique names remain recommended when widgets are addressed by actions.

Action Conditions

The condition attribute accepts active_is_true/active_is_false, sensitive_is_true/sensitive_is_false and visible_is_true/visible_is_false with a widget variable name. variable_is_true/variable_is_false test the current textual value of any widget directly. It also accepts command_is_true/ command_is_false and file_is_true/ file_is_false. For historical compatibility, an unknown condition is reported and otherwise ignored, text after the final closing parenthesis is ignored, and a missing closing parenthesis makes the rest of the attribute the argument. A recognised but inapplicable condition is false.

Toggle widgets also retain the legacy if true and if false prefixes inside action contents. These test the active state of the widget emitting the signal. When a prefixed action also has a condition attribute, the explicit condition is evaluated last and its result takes precedence for historical compatibility.

Shell Redirection

The contents of <action> and shell <input> directives are passed to the shell. Input redirection operators may be written directly, including without a space after the operator.

<input>wc -l </etc/passwd</input>
<action>sort <input.txt >output.txt</action>

The exact shell language remains determined by the command being run. Gtkdialog uses /bin/sh for ordinary commands; Bash-specific syntax must explicitly invoke Bash.

<action>bash -c "wc -l <(printf test)"</action>

Ordinary shell actions, shell input directives and command conditions are executed synchronously. A long-running command therefore blocks event processing in the GTK main loop until the command finishes. The progressbar input command is the exception: its output is consumed asynchronously by the GTK main loop.

Boolean command and file results accept true, yes, false, no, or a complete decimal integer. Zero is false and every other representable integer is true; malformed or overflowing numeric text is neither.

The older state-taking <input> implementations of button/togglebutton, checkbox, expander, check/radio menuitem, radiobutton and timer retain their historical rule: true, yes, or a numeric prefix whose value is exactly one enables the state; every other value disables it. This intentionally differs from the non-zero rule used by action conditions.

Keyboard Event Variables

Actions handling key press and release events receive KEY_VAL, KEY_SYM, KEY_UNI, KEY_MOD and KEY_RAW. KEY_SYM is an empty string when GDK has no symbolic name for the key value.

Imperative Construction

The legacy imperative directives execute while the dialog's widget tree is being constructed. Assignments store numeric values in process environment variables. Variable names use shell identifier syntax: a letter or underscore, followed by letters, digits or underscores.

<command assignment="n := 1"></command>
<while condition="n != 4">
	<text><label>Repeated widget</label></text>
	<command assignment="n := n + 1"></command>
</while>
<if condition="n = 4">
	<text><label>Final widget</label></text>
</if>

Expressions support decimal numbers, variables, addition, subtraction, multiplication, division, equality and inequality. Multiplication and division bind more tightly than addition and subtraction. A condition is false when its numeric value is zero and true otherwise. Undefined or malformed numeric values, division by zero and non-finite results produce a warning and evaluate as zero. Widgets produced by a true branch or by successive loop iterations are retained in their surrounding container.

Diagnostics

--no-warning suppresses warning-level diagnostics emitted by gtkdialog, including validation and child-command status warnings. Fatal parser and runtime errors are still reported, as is text written directly to standard error by a child command.

File Monitoring

Widgets supporting the file-monitor or auto-refresh tag attribute may also specify rate-limit as a non-negative number of milliseconds. An invalid value is ignored and the GIO monitor's default remains in effect.

File monitoring follows the named path when a writer atomically replaces the file with rename(), including repeated replacements. A monitor may also be established before the named file exists and notices its later creation.

Event-driven Files

--event-driven FILE loads FILE with /bin/sh, then starts a new gtkdialog process with the variables exported by that file. The file should therefore be valid POSIX shell and should define data and functions without launching gtkdialog itself. Its path may contain spaces or shell metacharacters.

The same file is installed as the new process's --include file, so it is loaded again before shell action and input commands. Bash-specific functions should be invoked through an explicit bash -c command.

Dialog source and presentation options are preserved when the new process is started, including --file, --program, --geometry, --space-expand, --space-fill and --styles. Packing states accept only true, yes or 1, and false, no or 0. An invalid state is ignored with a warning.

Error Locations

Line numbers in parser errors include newlines inside comments, double-quoted directive contents and double-quoted tag attributes.
